## 1. 现象摘要

跨 Gateway 群聊 burst 冒烟时，B（uid=100002，gateway-2）偶发收不齐 A 的消息：同一 `seq` 重复投递到 GW1、漏投 GW2。msgsvr 日志显示 fan-out 到 20001+20002 均成功，断点在 **hub → gateway-2**。

修复后：A→B、B→A 各 5 条双向互通；浏览器双窗口与 `go run . -burst 5` 稳定 PASS。

## 2. 根因清单（三个独立 Bug）

| ID | 层级 | 根因 | 表现 | 修复（hi-im-core / hi-im） |
|----|------|------|------|---------------------------|
| **Bug1** | bridge | IM 头 52B，bridge 仍按旧 48B 在 offset 4 读 nid（实为 Length） | 短文本 body length 被当成 destNid，路由到错误 gateway | `hiim::im::ReadDestNid` @ offset 24 |
| **Bug2** | 队列 | **DistQueue / RecvQueue 标注为 SPSC，实际为多生产者** | 队列槽位损坏 → 偶发丢包 / 重复路由 | 改为 `MpscQueue`（mutex + deque） |
| **Bug3** | 拼帧 | `FrameBuffer::TryPopFrame` 返回指向内部 `buf_` 的 span，`erase` 后悬垂 | msgsvr 连发 fan-out（sticky TCP）时第二帧 pop 污染第一帧 payload | `FrameView.payload` 改为 `vector`，erase 前拷贝 |

**smoke-group 补充（hi-im）**：gorilla/websocket 读 timeout 后连接状态损坏；A→B 后未读尽的下行帧导致 B→A 失败。burst 在阶段间 **重连 + 顺序 send/wait**（见 `examples/smoke-group/main.go`）。

## 3. Bug2 架构分析：设计意图 vs 实现

### 3.1 文档里写对了什么

`hi-im-core` §5.2 数据流：

```text
Reactor × N  ──recvq──►  Worker × M  ──Publish/AsyncSend──►  distq
Distributor  ──pop distq──►  sendq[reactor]  ──►  Reactor 写 TCP
```

要点 **「Distributor 单线程消费 async_send 队列，避免多写 sendq 竞态」** 是正确的：**SendQueue 必须是 SPSC**（仅 Distributor 写、对应 Reactor 读）。

### 3.2 文档里容易误导的地方

档 C / core 曾写「线程间队列：**SPSC 无锁环**」，但未按队列标注 **生产者数 × 消费者数**。Hub 单进程内实际有 **四类队列**：

| 队列 | 生产者 | 消费者 | 正确模型 | 修复前 |
|------|--------|--------|----------|--------|
| **ConnQueue[i]** | Listener → 固定 reactor | Reactor[i] | **SPSC** | ✓ |
| **RecvQueue[j]** | Reactor 0..N-1（`PickWorker(sid)`） | Worker[j] | **MPSC** | 误 SPSC |
| **DistQueue** | Worker 0..M-1（`Publish` / `AsyncSend`） | Distributor ×1 | **MPSC** | 误 SPSC |
| **SendQueue[i]** | Distributor ×1 | Reactor[i] | **SPSC** | ✓ |

Bug2 不是 Hub 分层架构错误，而是 **MPSC 场景实现成 SPSC**。多 Worker 并发 Push、单 Distributor Pop 时 SPSC 的 tail/head 竞态会导致内存损坏，表现为随机重复/漏路由。

### 3.3 与群聊链路的关系

档 C §11.1 双段 fan-out 第二段：

```text
msgsvr ──AsyncSend(destNid=20001)──► Hub BACKEND
msgsvr ──AsyncSend(destNid=20002)──► Hub BACKEND  （同一 TCP、极短间隔）
         bridge ──► FORWARD AsyncSend ──► 各 gateway
```

msgsvr 连发触发：**多 backend Worker 并发入 DistQueue** + **Reactor sticky 多帧入 RecvQueue**。二者都必须 MPSC。

## 4. 单 Hub 修复后仍须关注的点

| 项 | 说明 | 建议 |
|----|------|------|
| **Router 生命周期** | `nid_map` / `sub_table` 与 TCP 断开 | 断开即剔除；`AsyncSend` 失败可观测，不静默丢 |
| **SendQueue 背压** | Reactor 写慢 → DistQueue 满 | at-most-once + 显式 `QueueFull`；msgsvr best-effort fan-out |
| **端到端语义** | Hub 不保证「恰好一次」 | 业务 seq + 客户端排序；必要时 msgsvr 重试 |
| **MpscQueue 实现** | 当前 mutex + deque | 正确性优先；高 QPS 再考虑无锁 MPSC 或 per-worker 分片 distq |
| **可观测** | 路由静默丢失 | `[reactor]` / `[hub]` / `[bridge]` / `[distributor]` 带 dest_nid、seq；Prometheus `hiim_drop_total` |

## 5. 多 Hub 分片（Phase 2）新增的一致性风险

档 C §5.4：按 **NID 范围** 分片；gateway 只连本 shard FORWARD；`async_send(nid)` 跨 shard 时 **转发至 owner shard**。

队列 Bug 修好后，风险重心在 **分片边界**，不在单进程队列：

```text
                    ┌─ Shard-0（nid 20001）
msgsvr BACKEND ─────┤
                    └─ AsyncSend(20002) ──► 非本 shard ──► 转发 ──► Shard-1
```

| 风险 | 说明 | 架构建议 |
|------|------|----------|
| **nid 注册漂移** | GW 连 shard-1，AsyncSend 打到 shard-0 且未转发 | gateway 固定 `--shard-id`；NID→shard 单一路由函数 |
| **K8s 盲 LB** | Service 随机 Pod，nid 与 async_send 不在同一实例 | **禁止** Hub Deployment 盲 replicas++；StatefulSet / 分 shard Service |
| **跨 shard 重复** | 本地 + 转发各投一次 | 转发二选一；wire v2 `trace_id` 去重 |
| **分片迁移** | NID 换 shard，旧 map 仍生效 | 租约 / 双写窗口 / 版本号 |
| **publish 多副本** | 多 msgsvr SUB 同一 cmd | SUB=single 或 Kafka 分片；与 Hub 分片正交 |

**结论**：单 Hub 内是「入队 → 路由 → 出队」的 **进程内线性一致性**（MPSC + 单 consumer Distributor），不是分布式事务。多 Hub 后需在 **shard 所有权 + 跨 shard 转发语义** 上单独设计。

## 6. 架构建议（优先级）

### P0 — 单 Hub 生产前（已基本完成）

1. 文档与代码统一：**按队列标注 MPSC/SPSC**（见档 C §5.3.1）。  
2. FrameBuffer payload 拷贝（Bug3）；reactor 连 pop 多帧安全。  
3. CI：`TestStickyDualFanoutRouting`；可选 `HIIM_TEST_CONCURRENT=1`。  
4. 路由全链路日志 + queue drop 指标。

### P1 — 多 Hub Phase 2 前

1. **NID → shard** 配置与代码共用（gateway / msgsvr / hub 转发）。  
2. 跨 shard 转发：**at-most-once**，失败返回明确错误，msgsvr 可重试。  
3. gateway FORWARD **生命周期内 stick 单 shard**。  
4. 起草 ADR：跨 shard `AsyncSend` 状态机 + msgsvr multi-backend 连接模型。

### P2 — 性能演进

1. bench 后：per-worker SPSC distq + distributor 轮询，或 Vyukov MPSC。  
2. bus wire v2：`shard_id`、`trace_id`。  
3. 动态扩 shard：Hub 间控制面同步 nid 租约（可选）。

## 9. 一句话总结

**Bug2 = 档 C「Distributor 单线程 + 多 Worker 入队」与「全局 SPSC」实现不一致**；修复后 DistQueue/RecvQueue 用 MPSC，SendQueue/ConnQueue 保持 SPSC。上多 Hub 时重点转向 **NID 分片所有权与跨 shard 转发**，队列语义仍是必要基础而非充分条件。
