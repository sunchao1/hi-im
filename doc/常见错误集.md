# hi-im 常见错误集

本文档汇总 M6 群聊 Demo 与本地 Compose 联调时的高频问题，便于快速对照排查。

---

## 1. 打开了错误的 Demo 页面（8088 vs 8089）

### 现象

- 浏览器打开 `http://127.0.0.1:8088/group.html` 后 UI 异常
- 控制台或日志出现 `The string did not match the expected pattern` 等错误
- 行为与文档描述不一致

### 原因

| 端口 | 服务 | 说明 |
|------|------|------|
| **8088** | beehive 旧 demo（`beehive-demo-web`） | 另一套项目，**不是** hi-im M6 |
| **8089** | hi-im M6 demo（`hi-im-demo-web`） | `make m6-demo` 启动，见 `deploy/compose/.env` 的 `HIIM_DEMO_WEB_PORT` |

本机若 beehive 已占用 8088，hi-im 会在 `.env` 里把 Demo 端口改为 **8089**。

### 处理

1. 确认 `deploy/compose/.env` 中 `HIIM_DEMO_WEB_PORT`（常见为 `8089`）
2. 使用 `make m6-demo` 终端输出的 URL，例如：
   - 窗口 A：`http://127.0.0.1:8089/group.html?gw=1`
   - 窗口 B：`http://127.0.0.1:8089/group.html?gw=2`
3. 浏览器 **硬刷新**（Cmd+Shift+R / Ctrl+Shift+R）

## 2. ONLINE-ACK 超时

### 现象

- 页面日志：`register ok uid=... sid=...` 之后出现 **`ONLINE-ACK 超时`**
- 「创建群」不可用或后续操作失败

### 原因（链路）

ONLINE 完整路径：

```text
浏览器 WS → gateway 发 ONLINE(0x0101)
  → hub FORWARD → hub BACKEND → usrsvr 处理
  → usrsvr 回 ONLINE_ACK(0x0102) → gateway → 浏览器
```

典型失败模式：

| 组件 | 日志 | 含义 |
|------|------|------|
| gateway | `online: published` | gateway 已把 ONLINE 交给 hub |
| usrsvr | **无** `online: ok` | usrsvr 未收到或未处理 ONLINE |
| hub | `[bridge] forward publish cmd=0x101 err=no subscribers` | hub BACKEND **没有** `0x0101` 的订阅者，消息被丢弃 |

`readyz` / `healthy` 只表示进程与握手完成，**不保证** hub 路由表里仍有有效 SUB。  
单独 `docker restart usrsvr`（或 hub / gateway 部分重启）容易触发上述状态。

### 处理

**推荐（约 1～2 分钟）：**

```bash
cd hi-im
make m6-heal
```

等到终端出现 `M6 PASS: online probe OK` 后再打开浏览器。

**或完整重建：**

```bash
make m6-down
make m6-demo
```

**注意：** 不要只重启单个容器后立刻测 Demo；若必须重启，优先 `make m6-heal`，顺序为 hub → usrsvr/msgsvr → gateway。

### 自检命令

```bash
docker logs hi-im-gateway-1 2>&1 | grep 'online:' | tail -3
docker logs hi-im-usrsvr-1 2>&1 | grep 'online:' | tail -3   # 成功时应有 online: ok
docker logs hi-im-hub-1 2>&1 | grep bridge | tail -3          # no subscribers = SUB 丢失
curl -sf http://127.0.0.1:18180/readyz   # 端口见 .env HIIM_HEALTH_HOST_PORT
curl -sf http://127.0.0.1:28080/readyz
```

## 3. 「创建群」点了没反应 / 按钮是灰色

### 现象

- 「创建群」按钮发灰，点击无任何日志
- 或误以为已连接，实际未完成 ONLINE

### 原因

1. **未完成 ONLINE**：须先点「注册并连接」，日志出现 **`ONLINE ok`** 后才能建群
2. **旧版 UI**：按钮使用 HTML `disabled` 时，浏览器 **不触发** `click` 事件，表现为「完全没反应」（已在 demo 中改为样式禁用 + 点击提示）

### 处理

1. 先完成 ONLINE（见上一节若超时则 `make m6-heal`）
2. 硬刷新页面加载最新 `group-app.js`（URL 带 `?v=...` 缓存参数）
3. 确认日志中有 `ONLINE ok` 后再点「创建群」

## 4. 「加入群」点了没反应

### 现象

- 窗口 B 已 ONLINE，点「加入群」无成功提示
- 或感觉「毫无反应」

### 原因

1. **GID 未填写或为 0**：窗口 A 建群后，B 必须在 GID 栏填入 **同一数字**（例如 A 日志 `建群成功 gid=1`，B 填 `1`）
2. **未在窗口 B 先 ONLINE**：B 也需单独「注册并连接」并等到 `ONLINE ok`
3. **旧版 demo**：GID 为空时仅静默 return，缺少「加入群中…」等反馈（已改进）

### 正确流程

| 窗口 | URL 示例 | UID | 操作 |
|------|----------|-----|------|
| A | `.../group.html?gw=1` | 100001 | 注册并连接 → ONLINE ok → **创建群** → 记下 gid |
| B | `.../group.html?gw=2&gid=1` | 100002 | 注册并连接 → ONLINE ok → 确认 GID → **加入群** |

窗口 B 可在 URL 直接带 gid：`http://127.0.0.1:8089/group.html?gw=2&gid=1`

成功日志示例：`加群成功 gid=1`

### 若已有「加入群中 gid=…」但长时间无「加群成功」

与 [§2 ONLINE-ACK 超时](#2-online-ack-超时) 同类根因：hub BACKEND 丢失 **GROUP-JOIN** 的 SUB（`0x0305`），日志常见：

```bash
docker logs hi-im-hub-1 2>&1 | grep bridge | tail -5
# [bridge] forward publish cmd=0x305 err=no subscribers
```

此时 gateway / usrsvr 的 `readyz` 仍可能为 healthy，但 JOIN-ACK 永远回不来。

**处理：** 运行 `make m6-heal` 或 `make m6-down && make m6-demo`，硬刷新后再试。

自检：

```bash
docker logs hi-im-usrsvr-1 2>&1 | grep 'group-join' | tail -3   # 成功时应有 group-join: ok
```

## 5. 群消息收不到 / 只出现 `recv cmd=0x30c` / 单向丢消息

### 现象

- 窗口 B 能显示 `[uid xxx] 消息内容`，窗口 A 收不到（或反过来）
- 窗口 A 只有 `recv cmd=0x30c`，没有 `[uid xxx] ...`
- **单向丢消息**：例如 Chrome（gw=1）发的 +7～+10，Firefox（gw=2）只收到 +6、+11；msgsvr 日志全是 `fan-out ok`
- 发送方 Chrome 里能看到 +1～+11 连续，误以为对方也收到了 —— 那是 **本地回显**（灰色斜体），不是对方窗口

### 原因

1. **`0x30c` = GROUP_CHAT_ACK**（发送成功回执），不是群消息。群消息应是 **GROUP_CHAT（0x030B）**。
2. **ImGroupJoin 未成功**（ACK 头里 `cid` 与当前 WS 不一致）→ 该窗口收不到 `0x030B`。
3. **gateway 第二段 fan-out bug（已修）**：hub handler 里同步写 WebSocket，**gw=2（28081）** 下行队列堵住时，会出现「msgsvr fan-out ok 但 gateway-2 无 `downlink sent`」的跳跃丢包。
4. Demo **本地回显**与真实下行混在一起，容易误判。

### 处理

1. **重建并重启 gateway**（须含 downlink 队列 + `GetCidBySid` 修复）：

   ```bash
   make m6-heal
   # 或：make m6-down && make m6-demo
   ```

2. 两窗口 **Cmd+Shift+R 硬刷新** demo（当前版本 `?v=20260703i`）

3. 两窗口均 **重新点「注册并连接」→ ONLINE ok**，再建群/加群（gateway 重启后旧 WS 无效）

4. 测试时以 **接收方窗口** 日志为准；发送方灰色斜体仅为本地回显

### 自检

```bash
# msgsvr：应全部 fan-out ok
docker logs hi-im-msgsvr-1 2>&1 | grep 'group-chat fan-out' | tail -5

# gateway-2（Firefox / gw=2 接收方）：每条消息应有 recv + sent
docker logs hi-im-gateway-2-1 2>&1 | grep 'group-chat downlink' | tail -10

# 建群/加群后 ImGroup
docker logs hi-im-gateway-2-1 2>&1 | grep ImGroupJoin | tail -3
```

若 msgsvr `fan-out ok` 但 gateway-2 缺 `group-chat downlink: recv` 对应序号 → hub/下行问题；有 `recv` 无 `downlink sent` → 查 `send failed` / `queue full`。

### 全链路追踪（按 `text=` 关键字 grep）

以 `100041+3` 为例，一条消息应依次出现：

| 阶段 | 组件 | 日志关键字 |
|------|------|-----------|
| 1 | msgsvr | `group-chat: received` + `fan-out dest ok destNid=20001` |
| 2 | hub | `[bridge] backend async_send`（失败时才有；成功静默） |
| 3 | gateway-1 | `hub tcp recv text=100041+3` |
| 4 | gateway-1 | `group-chat downlink: recv text=100041+3` |
| 5 | gateway-1 | `downlink queued` → `ws write ok` |

**本次实测断点（gid=1）**：msgsvr 对 `100041+3/+4` 均 `fan-out dest ok`，但 **gateway-1 无 `hub tcp recv`** → 丢失在 **hub → gateway-1** 段，不是浏览器、不是 demo 展示问题。

```bash
# 一条命令查全链路（把 TEXT 换成消息内容）
TEXT='100041+3'
docker logs hi-im-msgsvr-1 2>&1 | grep "$TEXT"
docker logs hi-im-hub-1 2>&1 | grep -E 'bridge|distributor'
docker logs hi-im-gateway-1 2>&1 | grep "$TEXT"
docker logs hi-im-gateway-2-1 2>&1 | grep "$TEXT"
```

## 6. `make m6-down` 后提示 Network still in use

### 现象

```
Network hi-im_hiim Resource is still in use
```

### 原因

`demo-web` 等容器仍占用同一 Docker 网络（例如未加 `--profile demo` 时未停 demo 容器）。

### 处理

使用当前 Makefile 的 `make m6-down`（已包含 demo profile），或手动：

```bash
docker compose -f deploy/compose/docker-compose.yml \
  -f deploy/compose/docker-compose.m3.yml \
  -f deploy/compose/docker-compose.m6.yml \
  --env-file deploy/compose/.env \
  --profile infra --profile hub --profile biz --profile demo \
  down -v --remove-orphans
```

## 7. 端口与本机服务冲突

### 现象

- Compose 启动失败或 health 检查超时
- 本机已有 hiim-hub、beehive 等占用 18080 / 28888 / 8088

### 处理

复制并修改 `deploy/compose/.env`（参考 `.env.example`），例如：

```bash
HIIM_HEALTH_HOST_PORT=18180
HIIM_FORWARD_HOST_PORT=38988
HIIM_BACKEND_HOST_PORT=38989
HIIM_DEMO_WEB_PORT=8089
HIIM_GATEWAY1_HTTP_PORT=28080
HIIM_GATEWAY2_HTTP_PORT=28081
```

改端口后需重新 `make m6-down && make m6-demo`。

## 8. 终端冒烟与浏览器 Demo 的关系

| 命令 | 作用 |
|------|------|
| `make m6-smoke` | 容器内双 gateway 群聊冒烟（不依赖浏览器） |
| `make m6-demo` | 启动栈 + demo-web；结束时自动跑 ONLINE 探针 |
| `make m6-heal` | 有序重启 hub / 后端 / gateway 并验证 ONLINE |

浏览器 Demo 失败时，可先跑：

```bash
cd examples/smoke-group
HIIM_USRSVR_URL=http://127.0.0.1:8089 \
HIIM_GATEWAY_A_WS=ws://127.0.0.1:28080/ws \
go run . -online-only
```

输出 `M6 PASS: online probe OK` 表示 ONLINE 链路正常，问题更可能在浏览器缓存或 GID/双窗口操作。

## 9. 快速检查清单

- [ ] 打开的是 **8089**（或 `.env` 里配置的 `HIIM_DEMO_WEB_PORT`），不是 beehive 的 8088
- [ ] 已执行 `make m6-demo` 或 `make m6-heal`，且 ONLINE 探针通过
- [ ] 两个窗口分别使用 `?gw=1` / `?gw=2`，UID 为 100001 / 100002
- [ ] 两个窗口均出现 **`ONLINE ok`**
- [ ] 窗口 A 建群后，窗口 B **GID 已填**（或 URL `?gid=`）
- [ ] 页面已硬刷新，避免旧 JS 缓存
